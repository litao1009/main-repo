# novel-shadow-creator 可扩展性分析：从60章走向无上限的思考过程

> 记录时间：2026-06-02
> 分析对象：`/home/claw_studios/code/L1_novel_skill/SKILL.md`
> 核心问题：为什么60章后小说质量崩溃？如何突破？

---

## 阶段一：现状诊断（2026-06-02 第一轮）

### 用户描述的问题

用当前 skill 写小说，60 章之后「前言不搭后语」，质量崩溃。

### 分析发现

**60章不是代码限制，是设计规范限制。**

| 证据 | 位置 |
|------|------|
| `state_machine.py` 无 `max_chapter` 检查 | 代码全文 |
| `similarity_check.py` 无章节数逻辑 | 代码全文 |
| `state_machine.py` 唯一硬限制：`foreshadowing_active <= 15` | 第110行 |
| `similarity_check.py` 唯二阈值：BLEU < 0.3, Jaccard < 0.15 | 第73、109行 |
| 「60章」字样仅出现在设计描述中 | `SKILL.md` 第37、46、82、133行 |

### 崩溃的三大根因

| 根因 | 机制 | 后果 |
|------|------|------|
| **大纲枯竭** | `outline.json` 只有60章，61章起无规划 | AI 失去剧情指引 |
| **上下文膨胀** | `summaries.md` 逐章追加，`state.json` 事件无限堆积，全部加载到每章写作上下文 | token 随章数线性增长 |
| **30K token 窗口形同虚设** | SKILL.md 声称有滚动窗口，但实际未程序化截断 | 写第60章时上下文 ~25K token |

### 用户的初始洞察

> 「skill 是用到什么内容就取什么内容的强大技巧，可以分多层 MD 文档，这样就不需要全部加载了」

**这个洞察完全正确。** OpenCode skill 框架本身支持按需引用文件的机制。问题出在当前 skill 的设计把所有上下文都扁平化了（单文件 `summaries.md`、单文件 `state.json`）。

## 阶段二：分层方案初步推演（2026-06-02 第二轮）

### 用户追问

> 如果原小说有1000章，是不是抄袭小说的 skill 也会有1000章？这个1000章的 skill 是如何设计的？

### 分析结果

**源书章数 ≠ 影写章数。** 当前 skill 的设计哲学是「提取 DNA 再重组」，不是逐章映射。但假定确实要做1000章大长篇：

### 分层设计思路

```
outline/
├── volumes/
│   ├── volume_01.json      # 第1卷大纲
│   ├── volume_02.json      # 第2卷大纲
│   └── ...
├── arcs/
│   ├── arc_01_prompt.md    # 弧1详细写作指引
│   └── arc_02_prompt.md    # ...
└── master_outline.json     # 总纲（各卷一句话）

summaries/
├── chapter_001.md          # 单章摘要（~200字）
├── arc_01_summary.md       # 弧级摘要（~500字）
└── volume_01_summary.md    # 卷级摘要（~800字）

state/
├── active/
│   ├── state.json          # 当前弧活跃状态
│   └── foreshadowing.json  # 当前弧伏笔
├── archive/
│   └── arc_01/             # 写完即归档
└── global/
    ├── characters.json     # 全角色状态
    ├── world_facts.json    # 世界设定
    └── foreshadowing_master.json # 跨弧伏笔
```

**token 对比：写第65章时**

| 当前方案 | 改进方案 |
|---------|---------|
| 全部64章摘要 + 全部事件 + 全部大纲 | 当前弧大纲 + 弧级摘要 + 卷级摘要 + 最近5章摘要 + 活跃状态 |
| ~50K token | ~5-8K token |

## 阶段三：深层风险全量分析（2026-06-02 第二轮延续）

在此阶段识别出8大风险，按严重程度排序：

### 风险1：摘要级联失真（致命）

```
原始章节 → 章摘要（信息损失 ~70%）
章摘要 → 弧摘要（再损失 ~60%）
弧摘要 → 卷摘要（再损失 ~50%）
```

每级摘要都是 AI 用自己的理解重写的。到第5卷时，AI 读到的第1卷摘要可能与实际内容严重偏离。

**本质**：有损压缩不可逆。不是 bug，是信息论层面的必然损失。

**更危险的自指偏差**：卷3的摘要扭曲了卷1的事实 → 卷5基于扭曲的卷3摘要写作 → 偏差逐级放大 → 「跑偏螺旋」。

### 风险2：跨弧伏笔断裂（致命）

一个1000章长篇可能有30-50条活跃伏笔，其中一些跨越500章。当伏笔种植章节被归档后，除非有显式追踪，否则写第800章时 AI 完全不知情。

但如果把所有伏笔都注入上下文 → 50条伏笔描述占 ~3K token，又回到上下文膨胀问题。

### 风险3：角色漂移（严重）

- 角色状态随时间变化，需要的是「那一刻」的快照，不是最终状态
- 性格漂移更隐蔽：角色口头禅、决策逻辑、行为模式在漫长写作中不知不觉偏离初始设定

### 风险4：大纲递归生成的困境（严重）

不能一次性生成1000章大纲（超出AI输出上限）。必须递归生成：

```
卷概述 → 弧大纲 → 章大纲
```

问题：生成卷5大纲时，AI 还没写卷1-4。只能根据源书推测，不是根据影写版已写内容。导致后期大纲和前期内容脱节。

**两难**：
- 提前全生成 → 超出输出上限
- 逐卷延迟生成 → 与已写内容脱节

### 风险5：相邻章盲区（中等）

写第573章需要呼应第200章的一个细节 → AI 不知道。这是上下文窗口的物理限制，任何分层方案都无法完全解决。

### 风险6：similarity_check.py 的局限（中等）

- 每章都加载完整源书做 BLEU → O(n²) 级计算
- 不检查影写版**内部自相似** → 第700章可能不自觉地复用了第300章的桥段

### 风险7：文件数量负担（低）

1000+ 个小文件，人工回溯调试困难。

### 风险8：人工审阅成本（中等）

1000章 = ~110次审阅节点。每次30分钟 = 55小时纯审阅时间。

## 阶段四：转向「质量优先」（2026-06-02 第三轮）

### 用户纠正方向

> 「我并不需要非要原文章1000章我就要写成1000章，写的质量好、内容丰富精彩是第一优先级。」

### 重新定义问题

原问题：「如何在章数增长时保持质量？」
→ 重新定义：「什么样的架构能让**每章写作的上下文不随总章数增长**？」

### 答案：弧段自治 + 结构化快照

**核心原则**：每次写章时上下文恒定，不随总章数增长。

```
当前方案（线性退化）：
写第5章  → 上下文 ~3K  token
写第60章 → 上下文 ~25K token
写第200章→ 上下文 ~45K token（大纲也已枯竭）
                                                    ↑ 崩了

弧段自治方案（恒定）：
写第5章  → 当前弧大纲 + 前3章全文 + 弧快照 ≈ 6K token
写第60章 → 当前弧大纲 + 前3章全文 + 弧快照 ≈ 6K token
写第200章→ 当前弧大纲 + 前3章全文 + 弧快照 ≈ 6K token
写第500章→ 当前弧大纲 + 前3章全文 + 弧快照 ≈ 6K token
                                                    ↑ 恒定
```

### 弧段自治工作流

```
master_outline.json ← 只存每个弧的一句话方向（~500 token）

写弧2时：
  1. 读 master_outline.json → 弧2叙事方向
  2. 读 arc_1_snapshot.json → 弧1结束时的结构化状态
  3. 根据①②生成弧2详细章级大纲（10-20章）
  4. 逐章写作（每章上下文：弧2大纲 + arc_1_snapshot + 前3章全文 + style_fingerprint）
  5. 弧2完成 → 生成 arc_2_snapshot.json → 标记完成
  6. 人工审阅（每弧一次）
```

### 关键发明：结构化快照 arc_snapshot.json

**用结构化数据替代文本摘要。**

```json
{
  "arc": 3,
  "chapters_range": [45, 62],
  "character_states": {
    "林月": {
      "status": "alive",
      "location": "北域剑宗",
      "power_level": "金丹期",
      "emotional_state": "愤怒且迷茫",
      "key_trait_changes": ["从天真变得多疑"],
      "ongoing_plots": ["寻找师父下落"]
    }
  },
  "world_changes": {
    "北域剑宗": "被毁，已不存在"
  },
  "unresolved_questions": [
    "师父到底是死是活？(始于弧1)",
    "黑衣人是谁？(始于弧3本章)"
  ],
  "planted_foreshadowing": [
    {"desc": "西域商人提到"故人"", "planted_ch": 58, "target_arc": 5}
  ],
  "key_decisions": ["林月决定不回宗门，独自追查"],
  "next_arc_direction": "林月乔装进入西域，线索指向一个早已消失的家族"
}
```

**结构化优于文本摘要的原因**：陈述事实而非叙事重写，不具备「自指偏差」特性。

## 阶段五：「快照是否等于 memory agent？」—— 关键警觉（2026-06-02 第四轮）

### 用户提出的深层问题

> 「快照是不是需要后台去处理？生成小说的同时生成快照，快照保存的位置也需要考虑。」
> 「快照实际是一种类似 memory 的机制，但 memory 机制是需要后台去处理的。」

### 这个警觉完全正确，原因如下：

**当前 skill 的「底层」极度简单**：AI 遵循 SKILL.md 指令，用文件读写模拟状态管理。没有后台服务、数据库、memory agent。

**AI 既是作家又是秘书的矛盾**：

```
当前方案（AI 负担小）：
写第N章 → 更新 state.json（调一次脚本） → 完成

快照方案（AI 负担重）：
写第N章 → 输出小说正文 → 输出元数据 → 读 jsonl → 合成快照 → 集成
              ↑ 创作模式                  ↑ 管理模式
```

让同一个 AI 既创作又管理 → **创作质量被稀释**。

### 尝试解决：统一输出格式

让 AI 单次输出同时包含正文和结构化元数据：

```
AI 输出：
## chapter_body
[小说正文]

## chapter_meta
{ "character_changes": {...}, "new_events": [...], ... }
```

→ `chapter_body` 写入章节文件
→ `chapter_meta` 追加到 `arc_N_building.jsonl`

AI 只做一次思考，产出两份数据。无需切换模式。

### 但新的瓶颈出现

弧结束时，有人必须把 `arc_N_building.jsonl`（每章增量）**合成**为 `arc_N_snapshot.json`。

| 方案 | 做法 | 问题 |
|------|------|------|
| AI 合成 | 弧末 AI 读 jsonl 合成快照 | 弧长15+章时 jsonl 可能 ~3K token，挤占上下文 |
| Python 脚本合成 | 自动合并 | 逻辑复杂：合并人物状态、去重、冲突处理 |
| AI 直接凭记忆出快照 | 弧末凭记忆直接写 | AI 可能忘记弧初细节 |

**三种方案都不干净。**

## 阶段六：最终收敛 —— 最小代价方案（2026-06-02 第四轮）

### 核心决策：放弃「快照」概念，回归简单

不引入新概念。不引入增量机制。不要求 AI 切换模式。

只做三件事：

### 改动1：大纲不再预生成

```
旧：Phase B 一次性生成 outline.json（60章）
新：master_outline.json 只存每卷的一句话概述（~200 token）
   写入第N卷前，AI 才生成该卷的详细章级大纲
```

### 改动2：state.json 不再无限增长

```
旧：events 列表和 summaries 逐章累积，永远不清除
新：卷结束时 AI 将当前卷累积事件「归约」为一段固定长度文本（~300字）
   新卷开始时只加载上一卷的归约结论
```

### 改动3：summaries.md 不再逐章追加

```
旧：一个 summaries.md 文件，每章后追加 ~200字 → 线性膨胀
新：每卷结束生成一个 volume_N_context.md（固定格式，~800字）
```

`volume_N_context.md` 格式：

```
## 当前人物位置/状态
- 姓名：位置，情绪，目标

## 未解决的悬念
- ...

## 已种伏笔
- ...

## 世界观变化
- ...
```

### 写新章时的最终上下文组成

```
上一卷的 volume_N_context.md (~800字)
+ 当前卷大纲 (~300字)
+ 最近3章全文 (~4000字)
+ style_fingerprint.yaml (~1000字)
============================================
≈ 6000-8000 字，不随总章数增长
```

## 全方案收敛对比

| 维度 | 原始方案（快照+jsonl+合成） | 最终收敛方案（归约上下文） |
|------|---------------------------|------------------------|
| 新概念数 | 4+（快照、jsonl增量、合成、master_foreshadowing） | 1（volume_context.md） |
| AI 管理模式切换 | 逐章切换（输出正文+元数据） | 仅卷末切换（归约一次） |
| 需要新脚本 | 是（jsonl → 快照合成器） | 否 |
| token 稳定性 | 稳定 | 稳定 |
| 信息损失 | 低（结构化） | 中（文本归约有损失） |
| 实施难度 | 高 | 低 |
| 跨弧细节呼应 | 依赖 foreshadowing_master | 依赖 unresolved_questions |
| 风险 | AI 管理模式吞没创作质量 | 文本归约的轻度信息损失 |

## 最终判断

### 方案选择的权衡逻辑

「快照」方案（结构化数据、jsonl 增量、程序化合成）在理论上最优，信息损失最小。

但在 **opencode skill 框架的约束条件下**（无原生 memory agent、AI 同时承担多重角色、创作质量是唯一 KPI），理论上的最优解反而是实际上的次优解 —— 因为 AI 的管理负担会稀释创作质量。

**收敛方案的哲学**：接受一定程度的文本归约损失，换取 AI 能将 100% 的注意力放在「把小说写好」这一件事上。

### 不可消除的物理上限

| 极限 | 描述 | 无法消除的原因 |
|------|------|---------------|
| 跨弧细节呼应 | 写第500章时无法记得第50章的某个细节 | LLM 上下文窗口物理限制 |
| 文本归约信息损失 | 卷末归约时丢失「不重要的细节」 | 有损压缩必然损失 |
| 角色性格漂移 | 长写作中行为模式逐渐偏离 | 无自动化纠正手段 |

这些只能通过人工审阅来弥补。

### 结论

收敛方案可以将60章后质量崩溃的问题**从「一定会崩」降为「不确定的轻度衰减」**，代价是接受文本归约的轻度信息损失和每卷一次的人工审阅节点。

如果需要更高质量的保证（如减少文本归约损失），则需要 opencode 框架层级支持 memory agent 或持久化检索机制 —— 这已超出当前 skill 层面的修改范畴。
